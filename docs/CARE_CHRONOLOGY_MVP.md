# CareChronology × PainLocator — Prototype 0.1

**Branch:** feature/care-chronology-painlocator-mvp  
**Runtime:** static-only browser application, separate from the current PainLocator patient capture shell.  
**Route:** /care-chronology/ (also /care-chronology/index.html).  
**Status:** synthetic-data research prototype; **not a clinical or HIPAA-ready product**.

## What is implemented

- **Patient / clinical view:** different detail density, no autogenerated diagnosis.
- **Single event chronology:** visits, procedures, medications, laboratory measurements, patient reports, and example communications.
- **PainLocator body map:** reuses PainLocator's anatomy plates under /anatomy/ and normalized region coordinates.
- **Data trends:** patient-reported pain (0–10) and example hemoglobin values with no causal assertions.
- **Traceable record details:** explicit source name and reference, with unverified/imported provenance.
- **Filters and search** across event categories and text.
- **Two local file adapters:** PainLocator session JSON schema 1.x and selected FHIR R4 Bundle resource types.
- **Privacy protections:** fictional fixture; no automatic fetches, network writes, EHR credentials, browser persistence, analytics, or automated account connections. User must affirm that an imported file is fictional.
- **Dataset isolation:** imports replace the synthetic chronology on screen instead of interleaving patients. Reset returns to the built-in example.

All implementation is inside public/care-chronology/, which is copied to dist/ by PainLocator's existing build script. The existing PainLocator app, Clinical Anatomy Engine, data store, production UI, and authentication are unchanged.

## Open the prototype

- Local: npm install && npm run dev → http://localhost:5500/care-chronology/index.html
- Preview: use the preview deployment from this branch, **not the main production URL**, and append /care-chronology/.

## Anatomy / adapter behavior

PainLocator 1.x exported entries become patient-reported symptom events with:
- original createdAt, intensity (0–10), notes and quality;
- circles/ellipses/polygons represented as existing normalized (0–1) anchors;
- front/back/left/right region view and patient label;
- original entry id in source provenance.

The current UI projects anchor centroids onto the existing 2D plate. This is **not** validation of an anatomical diagnosis or perfect alignment across all rendered 2D/3D assets. A later production implementation should reuse CAE's full coordinates, anatomical layer registration and measurement tooling rather than duplicating projection.

The FHIR prototype currently reads only local *synthetic* R4 Bundles (Encounter, Condition, Observation, Procedure, MedicationRequest, DiagnosticReport, Communication); it does not implement SMART OAuth, server pagination, patient identity, deduplication, authorization scopes, data updates, medication reconciliation, or EHR write-back. It omits unsupported resources rather than inventing data. MyChart message access cannot be assumed.

## Safety and commercialization gates

**No real patient data** should be imported, deployed, logged, uploaded, shared, or used in a pilot with this branch. Local-only processing does not by itself establish healthcare regulatory compliance.

Before live data:
1. Medical and patient UX validation, accessibility audit, risk classification, terminology support, provenance tests.
2. Patient identity and encounter matching across disparate institutions, deduplication, source version handling and corrections, timezone fidelity.
3. Dedicated clinical hosting architecture, strict tenant isolation, encrypted data, consent and deletion flow, role-based access, audit, incident response and BAA review where applicable.
4. SMART on FHIR test against Epic sandbox and supported EHRs, OAuth PKCE, scope minimization, capability discovery, secure token handling, API paging and refresh.
5. Explicit clinician workflow and hospital agreement before considering DocumentReference attachment or any write-back.
6. Clinical legal/regulatory review of intended use, marketing claims, and any future AI-generated interpretations.
7. Representative patient groups and clinicians validating readability, anatomy accuracy and correct differentiation of reported vs clinically confirmed information.

**Do not call this "connected to Epic," "MyChart integration," "clinically validated," "FDA-cleared," or "HIPAA compliant."** It is an interoperability-ready *design prototype*, not a proven interoperability product.

## Suggested next engineering milestones

**S1.** Embed deep-links between PainLocator Capture/Review and CareChronology with explicit authorized session transfer, and test every body model/view on actual anatomy plates.

**S2.** Build patient identity and FHIR normalization in a dedicated backend using exclusively synthetic Epic sandbox resources. Show source deep-links, date provenance and data-quality warnings.

**S3.** Conduct usability sessions with clinicians and patients. Then design a compliant clinical deployment with audit/consent and EHR integration requirements.
